Examples make architecture consultant deliverable tracking easier to design because they reveal where a neat diagram meets messy work. The scenarios below are not claims about a particular company; they are test cases small architecture firms and design-project administrators can run against a template or software trial.

### Scenario 1: Structural backgrounds arrive without the agreed grid update

Create the record before the first follow-up. Capture Project and consultant, Discipline and deliverable package, Milestone and due date, then move it through define the consultant package and milestone and request and receive the controlled transmittal. If a milestone deliverable is missing or incomplete, do not improvise in a private message; assign the exception, set a review date, and preserve the evidence needed for the next decision. Close with an explicit outcome and reason. ### Scenario 2: Mechanical routing conflicts with the reflected ceiling plan

Create the record before the first follow-up. Capture Discipline and deliverable package, Milestone and due date, Expected format and model version, then move it through define the consultant package and milestone and request and receive the controlled transmittal. If the submitted version conflicts with another discipline, do not improvise in a private message; assign the exception, set a review date, and preserve the evidence needed for the next decision. Close with an explicit outcome and reason. ### Scenario 3: A civil revision changes an entrance elevation after coordination

Create the record before the first follow-up. Capture Milestone and due date, Expected format and model version, Transmittal and received time, then move it through define the consultant package and milestone and request and receive the controlled transmittal. If a consultant revision changes a previously coordinated dependency, do not improvise in a private message; assign the exception, set a review date, and preserve the evidence needed for the next decision. Close with an explicit outcome and reason.

## Debrief each scenario

After running a scenario, ask:

- Did the record make every open consultant deliverable needs one owner and a next review time?
- Did the record make completion requires recorded evidence that every consultant deliverable is received to the agreed milestone, reviewed against dependencies, and incorporated into the controlled project set?
- Did the record make automated reminders stop after verified completion or a documented closed reason?
- Did the record make keep controlled drawing, specification, rfi, and submittal repository as the system of record; only necessary coordination data belongs here?

Also check whether a new teammate could identify the owner, next action, and finish condition without opening another system.

## Convert scenarios into acceptance tests

Use the normal case, waiting case, and closed-without-completion case in every software demo. Require the vendor—or your own prototype—to show the full workflow rather than isolated feature screens. Export the resulting records and verify that the status history remains understandable.
