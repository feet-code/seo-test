Projects are called finished while files, credentials, ownership, maintenance instructions, and unresolved decisions remain across tools and conversations. The recurring failures are usually process-design problems rather than motivation problems. For freelancers and independent professional service businesses, these are the mistakes worth finding before buying or building software.


### 1. Sending a folder with no index

This usually survives because the workflow records activity but not the decision that activity was meant to produce. Add **Deliverable** at the point of work and enforce this guardrail: Access transfer follows appropriate security practice When the exception occurs, keep it visible instead of repairing it privately in email.

### 2. Sharing credentials in an unsafe channel

This usually survives because the workflow records activity but not the decision that activity was meant to produce. Add **Final file or system link** at the point of work and enforce this guardrail: Acceptance criteria come from the agreed scope When the exception occurs, keep it visible instead of repairing it privately in email.

### 3. Treating training as proof of client acceptance

This usually survives because the workflow records activity but not the decision that activity was meant to produce. Add **Owner after handoff** at the point of work and enforce this guardrail: Open items have owners, dates, and support boundaries When the exception occurs, keep it visible instead of repairing it privately in email.

### 4. Closing before unresolved items have owners and dates

This usually survives because the workflow records activity but not the decision that activity was meant to produce. Add **Access transfer status** at the point of work and enforce this guardrail: The handoff has a human-readable index When the exception occurs, keep it visible instead of repairing it privately in email.

## Audit five recent records

Pick five completed or abandoned examples and ask:

- Can we reconstruct client and project without asking the original owner?
- Can we reconstruct deliverable without asking the original owner?
- Can we reconstruct final file or system link without asking the original owner?
- Can we reconstruct owner after handoff without asking the original owner?
- Can we reconstruct access transfer status without asking the original owner?

If the answer is no, improve the capture point rather than adding a later reporting step. Reports cannot recover decisions that were never recorded.

## Use mistakes as software requirements

Turn every frequent failure into a testable requirement. “Better visibility” is vague; “show every record with no owner or next date” can be tested. “More automation” is vague; “stop reminders after the completion condition is recorded” can be tested.
